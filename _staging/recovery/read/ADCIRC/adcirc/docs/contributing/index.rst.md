| 185–215 | Maintainability — 기존 기능의 새 동작은 서브루틴(subroutine) 또는 함수(function), 새 기능은 모듈(module)의 후보라고 권장한다(188–193). GLOBAL 변수 추가를 강하게 지양하며 인수 전달과 상태 자료구조 또는 파생형(derived type)을 권장한다(195–204). DRY 원칙과 코드 청결을 요구한다(206–214). 원문: ```In all cases, adding additional variables to the ``GLOBAL`` module is highly discouraged. By``` (195); ```adding variables to the ``GLOBAL`` module, you are more likely to create spooky action at a``` (196); `distance, i.e., the values held in those variables can change due to things you can not` (197); `reason about in your local view of the code, and thus will be more challenging to understand.` (198); `Instead, you should  consider passing variables to subroutines and  functions as arguments.` (199); `Compilers are quite good at optimizing this and the performance impact is negligible.` (200); ```Additionally, just because  the variables are not within the ``GLOBAL`` module, but in some other``` (201); `module instead, does not mean that they are not global in their scope. We recommend that` (202); `when you need to maintain a state variable, you should consider using a data structure or` (203); `derived type rather than pointing at a variable in some global scope or other module.` (204). |
